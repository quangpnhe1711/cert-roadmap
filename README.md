# Cert Study Copilot

AI-powered personalised learning for IT certifications. Turns a certification, an
exam date and the learner's own course material into a day-by-day Vietnamese
study programme with grounded quizzes, weak-topic detection and adaptive
rescheduling.

Launch certification: **AWS Certified AI Practitioner (AIF-C01)**. Nothing in the
schema or the code names a provider - the catalogue is data.

## Local quick start

Everything below runs on your machine. No API key, no cloud account, no real
course material.

```bash
# 1. bootstrap: checks prerequisites, gets a JDK 21, starts PostgreSQL,
#    and generates a sample deck to upload
./scripts/dev-up.ps1          # Windows
./scripts/dev-up.sh           # macOS / Linux

# 2. backend  → http://localhost:8080
cd backend && ./mvnw spring-boot:run -Dspring-boot.run.profiles=local

# 3. frontend → http://localhost:5173
cd frontend && npm install && npm run dev
```

### Synthetic mode (default — no key, no network)

```powershell
./scripts/dev-up.ps1

$env:AI_ADAPTER = "fake"

cd backend
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
```

Every screen carries a *Synthetic AI* banner and the header chip reads
**Synthetic AI · Development**. Lessons and quizzes are fixture output: the
pipeline is real, the prose is not.

### Gemini mode (real model)

```powershell
$env:AI_ADAPTER = "gemini"
$env:GEMINI_API_KEY = "<your-key>"

cd backend
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
```

The header chip reads **Gemini · Connected**, the synthetic banner disappears,
and lessons and quizzes are generated by the provider. **No code changes and no
rebuild** — switching provider is two environment variables.

The key is read from the environment only. It is never written to a config file,
never stored in the database, never sent to the browser, and never logged. The
backend refuses to start with `AI_ADAPTER=gemini` and no key, so a missing
credential fails at boot rather than at a learner’s first lesson.

The frontend needs no change either: it asks the backend what provider is in use
rather than guessing from its own build.

Open **http://localhost:5173**, register an account, and follow the onboarding.
When it asks for material, upload **`local-data/sample-aif-c01.pdf`** — the
bootstrap script generated it.

**Reset the database** (drops the volume; Flyway migrates from V1 on the next
start):

```bash
./scripts/dev-down.ps1 -Purge     # Windows
./scripts/dev-down.sh --purge     # macOS / Linux
```

**Stop everything**: Ctrl+C the backend and frontend, then `./scripts/dev-down.ps1`
(or `.sh`). Uploaded files stay in `local-data/storage/` until you delete it.

The frontend needs no configuration: `npm run dev` proxies `/api` to port 8080.
`frontend/.env.example` documents the one override, for pointing at an API
somewhere else.

## Status

**Internal Alpha.** The engineering loop is complete and verified, and the whole
AI path has now been run end to end against a real provider. What is still
outstanding is *evaluation*: the product has not been validated against a real
AIF-C01 deck by a Vietnamese reviewer, so it is not an MVP Release Candidate and
not production ready. See [Release readiness](#release-readiness).

The core loop runs end to end:

```
register → choose certification → exam date + weekly hours → capacity check
        → upload PDF/PPTX → extract, structure, map to exam scope, coverage
        → deterministic schedule → Today → Vietnamese learning pack
        → original slide alongside → grounded quiz → deterministic grading
        → mastery + weak topics → replan → tomorrow pre-generated
        → final review exam from the validated question bank
```

Proven by `CoreLearningLoopIT` (services against a real PostgreSQL) and by
`e2e/core-loop.spec.ts` (a real browser against the running stack).

What is outstanding is **external**: a real AIF-C01 deck, a provider credential
and a Vietnamese reviewer. Everything that can be built and tested without them
has been. See [Release readiness](#release-readiness).

## Load-bearing decisions

**Three layers, not two.** `learning_unit` is derived from a `material_revision`
and knows nothing about any certification; exam relevance lives in
`unit_exam_mapping`; per-plan state lives in `plan_unit`; and only
`study_day_item` is rewritten by a replan. Because of that split, **replanning
never invalidates generated content and therefore costs nothing in model calls**,
and the same material can be mapped against a second certification without
rebuilding a single unit. `CoreLearningLoopIT.replanningCostsNothing` asserts
exactly that: after a replan the schedule differs, and the lesson rows, the
question rows and the total spend are byte-for-byte the same.

**One plan at a time, not one plan ever.** A partial unique index allows a single
plan per user in `DRAFT`, `ANALYZING`, `READY_FOR_REVIEW` or `ACTIVE` — two live
plans would compete for the same study hours, which multiplies the scheduler's
complexity for no MVP value. That is a limit on how many plans are *running*, not
on how many a learner has: `COMPLETED` and `ARCHIVED` plans stay in their history
and the next plan starts beside them. Creating a plan while one is `ACTIVE` is
refused with `ACTIVE_PLAN_EXISTS` (409) and the UI turns that into a choice —
continue the current plan, or archive it — rather than silently discarding a
schedule someone is part-way through. Archiving never deletes: completed study
days still point at the material revision behind them.

A finished plan is still useful. The week between the last study day and the exam
is exactly what the Final Review Exam is for, so `COMPLETED` keeps its progress,
its weak topics, its material and its exam, instead of dropping the learner back
into onboarding as though they had never had a plan.

**The scheduler is a pure function.** `SchedulerEngine.plan(PlanningContext)`
returns `Scheduled | Infeasible`. No database, no clock, no model, no mutable
state — every input, including today's date, arrives in the context. All four
replan triggers call the same function. An impossible plan returns `Infeasible`
with concrete options and **nothing is written**; a schedule that cannot be
finished is worse than an honest refusal. Twelve jqwik properties cover the
invariants.

**The AI boundary is enforced by the build, not by convention.** Every model call
goes through `AiGateway`, and ArchUnit forbids `planning.internal.scheduler`,
`assessment.internal.grading` and `assessment.internal.mastery` from depending on
`platform.ai`. See [Architecture rules](#architecture-rules).

**Cost is accounted before it is spent.** `AiGateway` reserves budget atomically,
calls the provider, and records actual cost for **every** attempt — including
attempts later rejected by parsing or validation, which consumed real tokens.
Recording only successes makes retries invisible to the budget precisely when
they are most frequent.

**Every question must prove where its answer came from.** A generated question
without a resolvable `sourceSpan`, or one that fails any of eight validation
checks, is discarded rather than repaired. Shipping fewer questions always beats
shipping one that is wrong, because a learner cannot tell the difference.

## Architecture rules

Rules live in `backend/src/test/java/com/certcopilot/architecture/` and fail the
build. Three tests share one set of rule objects:

| Test | Proves |
|---|---|
| `ArchitectureRulesTest` | the rules hold for production code |
| `ArchitectureRuleCoverageTest` | no rule passes vacuously — a rule matching nothing must be declared pending against a named slice, and a stale pending marker fails the build |
| `ArchitectureRuleVerificationTest` | each rule detects what it claims to — the same rule is run against a compliant fixture and a deliberately violating one |

Eight rules: R1–R3 keep the scheduler, grading and mastery free of the AI
platform; R4 keeps the platform free of the domain; **R5 keeps every model call
inside `AiGateway`**; R6 confines provider SDKs; R7 forbids module cycles; **R8
requires every HTTP route carrying a `planId` to reach an ownership check**,
directly or through the service it delegates to.

R8 exists because one route did not. `GET /plans/{planId}/units/{unitId}/pack`
took a plan id, never checked who was asking, and served a lesson generated from
the owner's private course material to any authenticated caller who knew the id —
spending the owner's AI budget to generate it if it did not exist yet. It looked
exactly like the seven routes beside it that were correct, which is why the guard
is a build rule and not a review checklist.

All rules currently cover real code; none is pending. The verifying fixtures in
`archfixture/` are compiled on purpose so the rules are demonstrably not toothless.

## AI operations

Six declared operations are the entire model surface. Anything not on this list
cannot reach a provider, because `AiGateway` requires a registered operation and
`LlmPort` is the only seam.

| Operation | Tier | Validator enforces |
|---|---|---|
| `material.structure.extract` | fast | sections tile the document exactly: contiguous, no gaps, no overlaps |
| `material.topics.extract` | fast | topics stay inside their section, difficulty 1–5 |
| `mapping.topic.to.task` | quality | task statement ids exist in the pinned exam version |
| `learning.pack.generate` | quality | material-origin blocks carry a page range; must-know coverage; n-gram overlap below threshold |
| `assessment.quiz.generate` | quality | eight checks, source span must resolve |
| `assessment.weakness.explain` | fast | may explain, may not emit a score or mastery verdict |

`assessment.weakness.explain` is reached from the progress screen, on demand: the
detection above it is arithmetic and always present, so the explanation is
generated only when a learner asks why — and when it is refused at the budget cap
the row keeps working without it.

Prompts live in `backend/src/main/resources/prompts/` as versioned files and hot
reload in development, because getting Vietnamese lesson quality right takes many
iterations and a redeploy per iteration would be the real schedule risk.

### Adapters

`LlmPort` has two implementations and nothing else may call it — architecture
rule R5 fails the build on a direct call, so the cache, the budget reservation
and the cost ledger cannot be skipped by adding a second call site.

| Adapter | `app.ai.adapter` | Credential | Used by |
|---|---|---|---|
| `FakeLlmAdapter` | `fake` (default) | none | development and CI |
| `GeminiLlmAdapter` | `gemini` | `GEMINI_API_KEY` | production |
| `AnthropicLlmAdapter` | `anthropic` | `ANTHROPIC_API_KEY` | production |

```bash
AI_ADAPTER=gemini    GEMINI_API_KEY=...    ./mvnw spring-boot:run
AI_ADAPTER=anthropic ANTHROPIC_API_KEY=... ./mvnw spring-boot:run
```

Both production adapters handle authentication, tier-to-model selection, request
mapping, forced JSON output, timeouts, provider error mapping, retry
classification, token extraction, cost inputs, cancellation and safe logging.
They are built on `java.net.http`, so there is no provider SDK to reconcile, and
each is covered by a contract test that runs the whole contract against a stub
server with no credential and no network.

**There is no provider fallback.** With `AI_ADAPTER=gemini`, a provider failure
is reported as a failure. It never falls back to the deterministic adapter, to a
second provider, or to a recorded response, because content that silently came
from a fixture while the UI said *Gemini* is the one outcome this whole seam
exists to prevent. Parser fallbacks — stripping a code fence, recovering an
object from surrounding text — are fine; provider fallbacks are not.

**The generating model is part of the cache key.** `AiGateway` folds
`llm.generationIdentity(tier)` into the artifact key’s generation half, so an
artifact produced by the fake adapter can never be served to a deployment running
a real model. Without it, flipping `AI_ADAPTER` would hand out fixture prose
under a provider’s name, and the ledger would agree.

#### Gemini configuration

| Variable | Default | Notes |
|---|---|---|
| `GEMINI_API_KEY` | *(none)* | required; boot fails without it |
| `GEMINI_FAST_MODEL` | `gemini-3.5-flash-lite` | structure, topics, weakness explanation |
| `GEMINI_QUALITY_MODEL` | `gemini-3.7-flash` | mapping, lessons, quiz |
| `GEMINI_FAST_THINKING` | `LOW` | `NONE` \| `LOW` \| `HIGH` \| `BUDGET:<n>` |
| `GEMINI_QUALITY_THINKING` | `BUDGET:0` | as above |
| `GEMINI_API_VERSION` | `v1beta` | pinned, not "latest" |

Gemini bills thinking tokens as output tokens **and counts them against
`maxOutputTokens`**. Unbudgeted, a model can spend a lesson’s entire allowance
reasoning and return `MAX_TOKENS` with nothing in it — paid for, and worthless.
`BUDGET:<n>` is therefore added *on top of* the operation’s own output ceiling.
Note that the 3.x *lite* models accept `thinkingLevel` and reject
`thinkingBudget`, while the flash and 2.5 models accept the budget: if you change
`GEMINI_*_MODEL`, check the matching `*_THINKING` value.

Model ids are configuration, never literals in domain code, and both defaults
were checked against the live API rather than taken from documentation. They are
current-generation on purpose: Google withdraws older ids from new keys —
`gemini-2.5-pro` and `gemini-2.5-flash-lite` already answer *"no longer available
to new users"* — so a default pinned to a previous generation is a default with
an expiry date. A retired model answers 404, which the adapter reports as a
permanent failure naming the model rather than as a mysterious outage.

**On the free tier, expect the run to pause.** Google limits free-tier requests
per minute and per day, and building one plan is dozens of calls. A 429 carries
the exact delay before the window reopens; the adapter honours it — bounded by
`max-retry-after-ms`, which is deliberately separate from `max-backoff-ms`
because our own backoff is a guess and the provider's number is a fact — and
retries up to `max-transport-attempts` times. A 429 spends no tokens, so this
costs time and nothing else. If a *daily* cap is reached the run fails honestly
rather than falling back: point `GEMINI_QUALITY_MODEL` at a model with headroom,
or use a paid key.

**Retries are split by layer on purpose.** The adapter retries transport
failures (429, 5xx, timeouts) itself, with backoff that honours `retry-after`;
no tokens were spent and nothing about the request needs to change. The gateway
retries content failures (parse, schema, domain), because those are the ones a
corrected prompt can fix. An authentication or malformed-request failure is
permanent on the first response — retrying a bad key three times only fails
three times as slowly.

**Nothing from the learner's material is ever logged.** Not the prompt, not the
output, and not a provider error message unless `log-provider-messages` is
explicitly turned on. Status, error type, token counts and sizes are, which is
what diagnosis actually needs.

**Prices are configuration, and unset by default.** `app.ai.model-prices` takes
the provider's published cents-per-million per model. With no entry the tier
estimate is used and every cost report says `TIER ESTIMATE` rather than quietly
presenting a guess as a measurement.

## Evaluation (D12)

The harness is implemented (`eval/EvaluationHarness.java`,
`eval/EvaluationRunnerIT.java`) and enforces the automatable gates:

- provenance present on every material-origin block
- source spans resolve against the actual source text
- every question anchored to a real task statement
- correct-answer counts match the question type
- ≥99% schema-valid after bounded retry
- release runs must cover every launch exam domain
- reviewer defect counts, each a hard gate at **zero**: critical factual errors,
  hallucinated source spans, wrong accepted answers, unintended multiple correct
  answers, conflicts resolved against the official guide

The defect counts are separate from the 1–5 scores on purpose. An average cannot
express "none of these": output can score 4.6 on factual correctness and still
contain one confidently wrong statement, and one confidently wrong statement is
what a learner carries into the exam.

Every run also reports **measured cost** from the ledger — per operation, with
rejected attempts, cache hits, tokens and retry overhead, and per material, per
learning unit and per study day against the D6 targets. Quality and cost are
decided together: output that passes every quality gate at four times the budget
has not passed.

```bash
# smoke: 8 units, run while iterating on a prompt
./mvnw verify -Dit.test=EvaluationRunnerIT -Deval.level=SMOKE

# release: 20-24 units, 80+ questions, real material, reviewer scores
./mvnw verify -Dit.test=EvaluationRunnerIT -Deval.level=RELEASE \
  -Deval.material=/path/to/real-course.pdf \
  -Deval.scores=factualCorrectness=4.6,grounding=4.7,examRelevance=4.4,\
vietnameseClarity=4.3,explanationUsefulness=4.3,quizQuality=4.3,\
shareAcceptedWithoutRewrite=0.92 \
  -Deval.findings=criticalFactualErrors=0,hallucinatedSourceSpans=0,\
quizWithWrongAcceptedAnswer=0,quizWithUnintendedMultipleCorrect=0,\
conflictsResolvedAgainstOfficial=0
```

Reports are written to `backend/target/eval-*.txt`.

**Not yet done, and cannot be faked:** the 1–5 quality scores and the defect
counts are human judgement
against real course material. A RELEASE run without `-Deval.scores` fails rather
than passing silently, and a run against the synthetic fixture labels itself as
not constituting a passing Release Eval. Prompt freeze requires **two consecutive
passing release runs**; a schedule that allows only one must label its output
`Internal Alpha / Pilot`, not a production MVP.

### Skips are named, and CI does not skip

Every run prints each skipped test with its reason, because `2 skipped` in a log
is indistinguishable from "the two tests that would have caught this did not
run".

Run verification with `-Dci.verification=true` (or with `CI` set) and a missing
database **fails** instead of skipping. A green build that quietly skipped every
test touching a database certifies nothing while looking exactly like one that
certified everything. Only the two explicitly gated utilities skip in CI:
`DumpDeckTest` (needs `-Ddump.deck`) and `EvaluationRunnerIT` (needs
`-Deval.level`).

## Toolchain

The build targets **Java 21** (virtual threads: the worker is I/O-bound on model
calls, so blocking handlers stay simple). The JDK is supplied by a Maven
toolchain rather than by `JAVA_HOME`, so Maven itself can run on any JDK.

`~/.m2/toolchains.xml`:

```xml
<toolchains>
  <toolchain>
    <type>jdk</type>
```

## Security and privacy

- Argon2id password hashing; short-lived access tokens with rotating, revocable
  refresh tokens.
- Authorisation at the service layer, deny by default, so jobs and admin paths
  pass the same gate as controllers.
- Uploads: real MIME sniffing, size and page caps, and an **exam-dump detector**
  that refuses leaked exam material at the door and again after extraction.
- Copyright is enforced in code, not policy: 12-gram overlap detection between
  generated text and the source, a cap on quoted spans, and no sharing feature at
  all.
- Original files are private, served only through short-lived HMAC-signed URLs
  after an ownership check.
- Learner material is never used for training and never shared between accounts.
- Prompts and model output are never written to a log.

All of the above is covered by `SecurityIT` (17 tests, service layer and HTTP
surface), which does not skip in CI. Writing and then auditing it found three
real defects, all fixed:

1. **An unauthorised route.** The learning-pack endpoint served one learner's
   generated lesson to another and could spend their budget. Fixed, with R8 to
   stop the class of bug returning.
2. **A content-type that was believed.** `sniffMime` fell back to the *declared*
   MIME when it recognised nothing, so any bytes could be admitted by claiming to
   be a PDF — three lines below a comment saying the declared type is evidence of
   nothing.
3. **A security response that rolled back.** `refresh` was `@Transactional`
   without `noRollbackFor`, so revoking every session on a replayed refresh token
   was undone by the exception that triggered it. The log said the sessions were
   dropped; they were not.

The pattern in all three: the intended behaviour was documented, and nothing
executed it.

## Deliberately not built

No message broker, no Redis, no vector database, no Kubernetes, no GraphQL, no
microservices. Retrieval is structural — document → section → learning unit →
page range — which is what the core loop actually needs. PostgreSQL leaves
`pgvector` available if semantic retrieval is ever required, so the decision is
deferred rather than foreclosed.

## Conventions

- All business rules live server side. The client renders and interacts.
- Writes are resource-oriented; screens that need composed data get purpose-built
  read models (`/today`, `/progress`), so no client re-implements composition.
- Async work answers `202` and is polled with backoff.
- Errors are RFC 9457 problem documents with a stable `code`; wording belongs to
  the client, which is what lets one API serve the Vietnamese web app and a
  future mobile client.
- Migrations are forward-only. Never drop a column in the same release that stops
  using it.
